Architecture
Vercel Sandbox runs on bare-metal EC2 hosts. A single EC2 metal instance hosts many sandboxes concurrently, one Firecracker microVM is booted per sandbox. A host-side orchestrator process manages each microVM's lifecycle: it prepares the drives and guest kernel, launches the microVM, and tears it down when the sandbox exits. Multiple microVMs share the same metal host but are isolated from each other by the Firecracker VMM.
The orchestrator does not run the Firecracker VMM directly. It launches Firecracker under a jailer, a companion binary that chroots the VMM into a restricted directory tree, places it in a dedicated cgroup, and applies namespace isolation so the VMM process itself is confined even if a guest-to-host bug is found. Each microVM boots its own dedicated guest kernel and has no shared running kernel with the host or with other sandboxes on the same metal instance.
Inside the microVM, an init process starts a Linux container (via runc/containerd) that runs the operator's code, either a custom container image the operator supplied or Vercel's default image. The Linux namespaces around this container exist for developer experience, not for security; the Firecracker microVM is the actual security boundary. Operator-supplied code therefore runs two layers removed from the EC2 host: first the Linux container, then the Firecracker microVM.

Focus areas
We are particularly interested in:
Escape from the Firecracker microVM to the EC2 host OS
Cross-tenant read, modification, or code execution against a sandbox you do not own
Sandbox firewall bypass that reaches destinations the operator did not authorize, especially with credential or data exfiltration
Retrieval of credentials configured through credential brokering via a Vercel-side defect
Web or API vulnerabilities in the sandbox control plane (the Vercel REST API behind the sandbox CLI and @vercel/sandbox), such as broken authorization that grants access to or control over sandboxes you do not own
Cross-tenant denial of service (crashing or destabilizing other tenants on the same host)
In Scope
The security boundary of Vercel Sandbox is the Firecracker microVM. Each sandbox runs inside its own microVM with a dedicated guest kernel on a shared EC2 metal host. Inside the microVM, a Linux container runs the operator's code (a custom container image or the default image). The Linux namespaces around that container exist for developer experience, not for security ; we already know of multiple ways to escape them to the Firecracker guest OS, and we do not consider that a sandbox escape.
A real sandbox escape, for the purpose of this challenge, is any technique that does one of the following:
Escapes from the Firecracker microVM to the EC2 host OS (the actual trust boundary).
Reads or modifies data belonging to another tenant (a sandbox you do not own), including files, environment, secrets, memory, or network traffic.
Executes code on the EC2 host or in another tenant's sandbox.
Crashing or destabilizing other tenants' sandboxes on the same host (cross-tenant denial of service).
Sandbox firewall bypass is also in scope and includes anything that defeats the security controls the operator configured on the sandbox, even when it does not reach the host:
Bypassing the sandbox network firewall (deny-all, domain allowlists, subnets.allow / subnets.deny, CIDR-only allow) to reach destinations the operator did not authorize.
Retrieving credentials configured through credential brokering (injected OIDC tokens, forwarded auth headers, etc.) without relying on a vulnerability in a third-party website that reflects those headers back.
The sandbox control plane is in scope as well: the Vercel-operated REST API that the sandbox CLI and @vercel/sandbox call to create, configure, and manage sandboxes. Classic web and API vulnerabilities against that API are in scope when they cross the sandbox trust boundary — for example broken authorization or IDOR that lets you read or modify another tenant's sandboxes, sessions, or network / credential configuration; an authentication or access-control bypass on a sandbox control-plane endpoint; or any other control-plane defect that lets you act on a sandbox you do not own. You do not need to enumerate the endpoints: if the sandbox client consumes it, it is in scope.
This covers only the sandbox control plane. Other Vercel REST APIs that are not part of the Sandbox product are not in scope (see Out of scope).
Out of scope
The following are explicitly out of scope and will not be rewarded. If you are unsure whether a finding falls into one of these categories, open a clarification discussion before spending time on a PoC.
Linux container namespace escapes that only reach the Firecracker guest OS (PID, mount, net, disk, or device namespaces). We are aware of multiple ways to do this and consider the namespaces a developer-experience feature, not a security boundary. A finding that only escapes the container to the firecracker guest OS ; without reaching the EC2 host, another tenant, or defeating a firewall/credential control ; is out of scope.
Denial of service against your own sandbox (crashing, hanging, or exhausting resources in a sandbox you own). This is trivially reproducible and not rewarded.
Vulnerabilities in third-party websites that reflect credential-brokering headers back to the sandbox. Credential retrieval is in scope only when the headers are exposed through a Vercel-side defect, not when an external destination echoes them.
Behavior the documentation tells operators to configure differently. Where the Sandbox docs document a limitation at the time of submission and direct operators to a different configuration, exercising that limitation is intended behavior, not a vulnerability ; for example combining a domain allowlist with subnets.allow, or relying on a CIDR-only policy to restrict DNS, which the Sandbox firewall docs warn against. If the documented guidance is unclear or absent, open a clarification discussion rather than submitting a report.
Already-public Firecracker or any other software component CVEs reported as a version match. Telling us that the Firecracker build we run is affected by a CVE or public advisory that exists at the time of submission is not a finding on its own. A CVE being present in a version does not mean it is exploitable here: the jailer, seccomp profile, cgroups, and device configuration around the VMM may put it out of reach in practice. Advisory links, version comparisons, and public exploit code that we cannot see working against a live sandbox are out of scope. If you weaponize one, it is in scope: a public upstream Firecracker vulnerability that you drive to a real escape to the EC2 host or to another tenant on a live Vercel Sandbox is eligible, and is paid at the impact you demonstrate.
Custom-kernel or custom-VMM attacks that require a kernel or Firecracker build the operator cannot supply. The guest kernel is baked into the EC2 instance and firecracker microvm; per-sandbox kernel override and custom Firecracker microVM kernels are not supported, so attacks that require supplying a malicious kernel are not reachable by an operator.
Build-phase Dockerfile / Containerfile build environment issues (image build, build context, cache, registry auth at build time). These belong to a different product boundary and are tracked separately. The execution phase that backs Vercel Sandbox is in scope; known execution-phase findings are listed in the next section.
Vercel Container Registry (VCR) issues ; registry auth, blob push, OIDC vercel scope, and VCR control plane are out of scope.
Static-analysis-only findings. A confirmed report requires a working live PoC against a vercel sandbox.
Vulnerabilities in services Vercel does not operate (e.g., Datadog, AWS) even if their credentials are reachable from a sandbox; report the Vercel-side reachability, not the third-party bug.
The @vercel/sandbox SDK and runtime that operators use to create and configure sandboxes. These should be used by researchers to consume the Sandbox API and create their test environments, but vulnerabilities within this package (the client-side code) are not in scope. The server-side sandbox control plane API these clients call is in scope — see In Scope.
Other Vercel REST APIs not associated with Sandbox. Only the sandbox control plane — the API consumed by the sandbox CLI / @vercel/sandbox to create and manage sandboxes — is in scope. The broader Vercel platform API (account, team, project, deployment, dashboard, billing, and other non-Sandbox endpoints) is not part of this challenge; report those to the appropriate Vercel HackerOne program.
Known findings
The following container-escape and credential-brokering classes have already been confirmed and documented internally. Reports that duplicate these root causes will be closed as duplicate and are not eligible for bounty, unless the report demonstrates a materially new impact (a new escape path to the EC2 host, cross-tenant reach, or a previously-unknown host write primitive). The primitive itself is a duplicate; any new impact is paid at the new impact's tier.
Container → Firecracker guest OS namespace escape
These are known, the Linux container is not the security boundary:
Writable /proc/sys/kernel/core_pattern combined with the shared /volumes/opt/vercel bind mount → uid 0 in the microVM initial PID/mount namespace.
All 41 Linux capabilities granted to the sandbox container.
Host /dev bind-mounted into the sandbox.
Seccomp profile with DefaultAction: ActAllow and a bypassable AF_VSOCK rule.
mknod + mount of the microVM system disk (/dev/vda) from inside the container.
One-syscall escape via writable /proc/sys/kernel/modprobe and /sys/kernel/uevent_helper combined with the /opt/vercel/ read-write bind mount.
Post-escape host-side surface
These are also known, not rewarded absent a new host-compromise primitive:
Unauthenticated host service on vsock 2050 exposing resource-usage, proxy-CA, cache-oracle, and OCI-image-config read/write RPCs.
Post-escape outer-namespace depth:
containerd.sock,
ipc.sock,
APM/metrics sockets world-accessible from the escaped context.
Sibling container spawn via the host control socket (still Firecracker-bounded, not EC2).
CAP_SYS_ADMIN + unrestricted /proc/sys writes (kernel sysctl surface, dmesg / kptr leaks).
DogStatsD / metrics vsock forwarder injection with no demonstrated cross-tenant impact.
sandbox-init Ed25519 key extraction.
Credential brokering / observability header leakage
Platform injects x-vercel-oidc-token, x-vercel-protection-bypass, and x-vercel-proxy-signature into every request without stripping. Capture of these headers from a sandbox workload is in scope only if the exfiltration channel is a Vercel-side defect, not a third-party site reflecting them.
A report that chains one of the above known primitives into a new host-compromise, cross-tenant, or firewall-bypass-with-exfil impact is still eligible for bounty at the severity of the new impact demonstrated.
Bounty table: Severity Guidelines
Bounties are paid per report, scoped to a single root cause. The maximum payout is $50,000 USD for a vulnerability that allows a threat actor to read or modify information belonging to another Vercel tenant. Severity is assigned by Vercel triage based on the maximum demonstrable impact of the root cause, not the reporter's self-assessment. A single report is paid at the severity of the highest-impact variant demonstrated; partial impact is paid at the partial tier.
Critical
Bounty: $25,000 – $50,000 USD
Firecracker microVM escape to the EC2 host OS ; e.g., a 0-day in the Firecracker VMM, jailer, snapshot/restore, or virtio device path that yields code execution on the host.
Cross-tenant read or modification of another tenant's sandbox data (files, environment, secrets, memory, or network traffic) without that tenant's cooperation.
Cross-tenant remote code execution ; running attacker-controlled code in another tenant's sandbox or on the EC2 host.
Escape from the microVM to the EC2 host via a Vercel-side misconfiguration or host-service vulnerability (e.g., host-service vsock RPC abuse that escalates to host compromise).
High
Bounty: $10,000 – $25,000 USD
Sandbox firewall bypass that exfiltrates credentials configured through credential brokering (OIDC tokens, forwarded auth headers) to an attacker-controlled destination.
Network firewall evasion that defeats deny-all, domain allowlists, or subnets.deny to exfiltrate operator data to a destination the operator did not authorize.
Cross-tenant denial of service ; crashing, hanging, or destabilizing other tenants' sandboxes on the same EC2 host.
VM-level crash or instability that affects other tenants on the host (not just your own sandbox).
MMDS secret disclosure ; reading populated MMDS content (Datadog, credentials, or equivalent) from a sandbox under deny-all or CIDR deny.
Medium
Bounty: $5,000 – $10,000 USD
Sandbox firewall policy boundary violation without demonstrated secret exfiltration (e.g., reaching a destination that should be denied but without exfiltrating operator data).
Credential-brokering header exposure to a destination that does not obviously reflect them, where the exposure is a Vercel-side defect.
Unauthenticated read-only host-service RPC abuse from an escaped context that exposes host billing data, the proxy CA certificate, or a cross-sandbox cache oracle.
Sandbox network-policy persistence bugs with security impact (e.g., policy updates not persisted on resume, stale SDK readback) that weaken an operator's configured posture.
ForwardURL / transform rule bypass that misroutes authenticated traffic to an attacker-influenced origin.
Low
Bounty: $1,000 – $5,000 USD
A demonstrated gap between the policy an operator configured and the behavior actually enforced. To qualify, a report needs a live PoC on a real sandbox, must not be explained by the documentation, and must be something we would change.
Correct but immaterial findings are closed Informative with no bounty.
A sandbox blocking more than the operator configured is a product bug, not a security finding.
Silent fail-open. A configured control is accepted by the API but not enforced, with no error, warning, or readback that would tell the operator.
Policy normalization mismatches. A value is accepted but enforced differently than written: case, IDN, trailing dot, wildcard depth, port suffix, unmasked CIDR, or allow/deny precedence. All inputs sharing one parsing root cause are one report.
Policy lifecycle gaps. Policy not reapplied identically across resume, snapshot/restore, or restart; stale readback; an unfiltered window at sandbox boot before enforcement loads.
Brokered-credential hygiene. A brokered token readable inside your own sandbox from somewhere it need not be (logs, process args, environment, on-disk temp), or with scope, audience, or lifetime broader than the operation requires.
Cross-tenant near-misses. Evidence of another tenant's existence, timing, or activity on the shared host, with no content recoverable.
Identifier predictability. Sandbox, session, or credential identifiers with materially less entropy than required, without a demonstrated use.
Quota or metering evasion with no cross-tenant or host effect.
Host implementation disclosure that materially narrows an attack path (host build, configuration, or topology) with no secrets exposed. A fingerprint with no bearing on reachability is Informative.
Not eligible (closed Informative)
Valid observations, not bounty findings: logging and audit-trail gaps where enforcement itself held (denied egress not logged or counted, policy changes with no audit trail); version banners on sandbox-internal endpoints; missing security headers; verbose errors or opaque status codes with no security consequence; capability or configuration inventories with no demonstrated reachability; documentation and best-practice suggestions; raw scanner output.
Rules of engagement
One vulnerability per report, unless you must chain issues to demonstrate impact.
Duplicates: we award the first valid, fully reproducible report of a root cause. Later reports of the same root cause are duplicates. A new impact from a known primitive is paid at the new impact's tier.
Internal duplicates: we cross-reference every submission against our internal vulnerability tracker, not only the Known findings published here. A report matching a finding already on file is closed as a duplicate even when it is not listed on this page, including findings we have chosen not to fix; we will give you the date it was recorded and a rationale.
Root cause consolidation: multiple vulnerabilities caused by one underlying issue receive one bounty.
Provide detailed reproduction steps and a zip of working proof-of-concept code. Reports we cannot reproduce are not eligible.
Make a good faith effort to avoid privacy violations, destruction of data, and interruption or degradation of Vercel services.
Only interact with accounts you own, or with the explicit written permission of the account holder.
Do not access more data than necessary to prove the vulnerability. Stop immediately if you encounter personal data or secrets that are not yours; do not download them; redact them from the report.
Do not install persistent backdoors. Do not maintain access after you have a PoC. Do not modify host or tenant state beyond what is required to demonstrate impact.
No social engineering (phishing, vishing, smishing) of Vercel employees, customers, or researchers.
Do not threaten Vercel or HackerOne staff.
Security scanners against Vercel-operated endpoints: cap at 5 queries per second. No volumetric DoS.
Do not submit AI-generated reports without personally verifying a working PoC and real impact.
All testing must comply with applicable law.
Testing guidelines
The short version: use your own accounts, use two of your own accounts for cross-tenant tests, and stop the moment you confirm cross-tenant access.
Warning: Testing accounts, projects, or sandboxes you do not own — or continuing after a successful bypass to enumerate, dump, persist, or otherwise act maliciously against another tenant or the host — is outside Safe Harbor, makes the report ineligible, and may be treated as abuse.
Accounts
Create your own Vercel accounts for testing. Do not test against accounts, projects, or sandboxes you do not own.
Sign up at vercel.com with your HackerOne alias (username@wearehackerone.com; aliases supported). Use those accounts for all Sandbox API traffic so we can distinguish research from abuse.
Hobby is free and enough to start. Pro has higher sandbox quotas — see Sandbox pricing.
All testing happens inside accounts you control. That keeps your work isolated from real customer workloads and gives you a clean environment to reproduce from.
Do not attempt to access, enumerate, or probe other Vercel tenants' accounts, projects, or sandboxes — except as described in Cross-tenant testing below.
Cross-tenant testing
Cross-tenant impact is the highest-value class and the highest risk to customers. Follow this exactly:
Always use two accounts you own (attacker and victim). Reproduce the cross-tenant access entirely between those accounts.
Stop at confirmation. If you cannot reproduce with two accounts you own — for example because the vulnerability appears to depend on a target you do not control — stop after a single confirmation. Do not enumerate, dump, or explore the other tenant's data. Record what you observed, redact third-party data, and report.
Never exfiltrate, persist, or further explore another tenant's data. A single confirmation that the boundary broke is enough. Going further risks real customer data, is outside Safe Harbor, and will disqualify the report.
The goal is to prove the boundary broke, not to maximize impact. A clean, minimal confirmation pays the same as a noisy one — and keeps the program open for everyone.

Configurations to test
Try each surface in both default and hardened modes, and look for gaps between what the operator configured and what the sandbox actually enforces.
Network firewall — deny-all, domain allowlists, subnets.allow / subnets.deny, CIDR-only allow. Confirm the sandbox actually blocks what the policy says it blocks; look for destinations that are reachable but should not be.
Credential brokering — injected OIDC tokens, forwarded auth headers, forwardURL / transform rules. Try to retrieve a brokered credential without relying on a third-party website reflecting it back.
Resources and lifecycle — CPU, memory, disk, persistence, snapshots. Look for cross-tenant side effects (for example, a crash that affects other sandboxes on the same host).
Host services — anything reachable from inside the sandbox that is not on the public internet (host-facing RPCs, metadata services).
In-scope and out-of-scope classes are defined in In Scope and Out of scope above.

Disclosure policy
This program uses Limited Coordinated Vulnerability Disclosure. Reports start private. Public disclosure of vulnerability details is not permitted until the embargo below has expired, and then only as described in this section.
This policy prevails over HackerOne's disclosure guidelines where they conflict. On-platform disclosure on HackerOne requires explicit Vercel approval (mutual agreement). Silence is not approval. Resolved reports will not auto-disclose.
What you may say at any time
You may state that you are participating in the Vercel Sandbox Escape Challenge, that you submitted a report, and that a bounty was awarded (you may share the amount). You may link the public program page and Vercel's public announcement.
Before the embargo ends, you may not publish or share with anyone outside this HackerOne report:
Reproduction steps, proof-of-concept code, exploits, payloads, or "how we broke it" write-ups
Screenshots, videos, logs, or memory dumps from a sandbox, host, or other tenant
Internal host services, vsock endpoints, MMDS contents, brokered credentials, tokens, cookies, or customer data
Sandbox IDs, team IDs, project IDs, or host identifiers that are not yours
Enough technical detail that a skilled reader could reproduce the issue
That includes blogs, social media, conference talks, GitHub repositories, Discord/Slack, pastebins, and private shares with people who are not collaborators on the HackerOne report.

Do not publicly disclose vulnerability details until all of the following are true:
The report is closed (Resolved, Informative, Not applicable, Duplicate, or Spam).
1 December 2026 has passed (90 days after program close on 1 September 2026), or Vercel has written to you that this report is cleared for disclosure earlier.
If the finding is Critical or High and still unpatched in production on 1 December 2026, Vercel may extend the embargo once, in writing on the report, by up to 90 days (no later than 1 March 2027). One extension maximum. Vercel will state the new date on the report.
If Vercel has not approved or denied a disclosure request within 14 days after the applicable embargo date, you may publish an external write-up (blog, talk) with the redactions in "Never disclose" below. That does not publish the HackerOne report; on-platform disclosure still needs Vercel approval.
Vercel paying a bounty is not permission to disclose and is not payment for silence. We pay for the report. We still need time to patch production and other reports in the same class.

External (blog, talk, research paper, video) ; allowed after the embargo. Send Vercel the draft 7 days before publishing so we can flag remaining production risk, customer data, or sibling reports that are still embargoed. We will not veto tone or credit. Safe Harbor
We consider security research conducted in accordance with this policy as authorized conduct under applicable anti-hacking laws, including the Computer Fraud and Abuse Act, the DMCA, and similar laws. We will not pursue civil or criminal action, or send a cease-and-desist, against researchers who follow this policy in good faith.
This protection does not extend to third parties. If in doubt, ask before taking an action you think may be outside this policy.
Safe Harbor does not cover: testing out-of-scope assets, accessing or retaining another tenant's data beyond a single confirmation, volumetric DoS, social engineering, or public disclosure of embargoed vulnerability details or working exploits.
